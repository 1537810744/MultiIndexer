# 多链区块链浏览器 — 可行性分析与架构设计

---

## 一、什么是区块链浏览器？

区块链浏览器是区块链世界的"搜索引擎"。用户输入区块高度、交易哈希、钱包地址，
浏览器从链上拉取并展示所有相关数据。

**参考产品：**
- [OKLink](https://www.oklink.com/) — 支持 30+ 链，统一搜索，跨链地址关联
- [Tokenview](https://blockchain.tokenview.io/) — 支持 200+ 链，全量数据索引
- [Blockscout](https://www.blockscout.com/) — 最流行的开源 EVM 浏览器（Elixir）

**核心功能：**
```
┌─────────────────────────────────────────────────────┐
│                   区块链浏览器                         │
│                                                      │
│  搜索栏：输入 地址 / 交易哈希 / 区块高度 / 代币名      │
│                                                      │
│  ├── 首页仪表盘                                      │
│  │   ├── 最新区块列表（高度、时间、出块者、交易数）      │
│  │   ├── 最新交易列表（哈希、from→to、金额、时间）      │
│  │   └── 网络统计（TPS、总交易数、总地址数、总区块数）   │
│  │                                                   │
│  ├── 区块详情                                        │
│  │   └── 区块高度、哈希、时间、矿工/验证者、Gas用量     │
│  │       该区块包含的所有交易列表                       │
│  │                                                   │
│  ├── 交易详情                                        │
│  │   └── 交易哈希、状态、区块、时间、from、to          │
│  │       金额、Gas费、输入数据（Input Data）            │
│  │       事件日志（Logs）                              │
│  │                                                   │
│  ├── 地址详情                                        │
│  │   └── 地址余额、交易数、首次/最后活动时间             │
│  │       该地址的所有交易历史                           │
│  │       该地址持有的代币列表（ERC-20/NFT）             │
│  │       该地址的代币转入/转出记录                      │
│  │                                                   │
│  ├── 代币详情                                        │
│  │   └── 代币名称、符号、精度、合约地址、总供应量        │
│  │       持有者列表、转账记录                          │
│  │                                                   │
│  └── 多链切换                                        │
│      └── ETH / BSC / Polygon / Solana / TRON ...     │
└─────────────────────────────────────────────────────┘
```

## 二、行业参考：它们是怎么做的？

### 2.1 Blockscout（最流行的开源浏览器）

```
技术栈：Elixir + Phoenix + PostgreSQL + Redis
架构：

  Geth/Erigon 节点
       │
       ├── eth_subscribe (WebSocket) → 实时新区块
       ├── eth_getBlockByNumber      → 历史区块回填
       ├── eth_getLogs               → 事件日志
       ├── trace_replayBlockTraces   → 内部交易
       └── eth_getBalance            → 地址余额
       │
       ▼
  Indexer Pipeline（索引管道）
  ┌──────────────────────────────────────────────┐
  │ Block Fetcher → 区块 + 交易                   │
  │ Internal Tx Fetcher → 内部调用（合约间转账）    │
  │ Coin Balance Fetcher → 地址余额更新            │
  │ Token Fetcher → ERC-20/721 代币数据            │
  │ Token Balance Fetcher → 地址的代币持仓          │
  │ Contract Code Fetcher → 合约字节码              │
  │ BlocksBeyondConsensus → 链重组处理              │
  └──────────────────────────────────────────────┘
       │
       ▼
  PostgreSQL（核心表）
  ├── blocks           — 区块头信息
  ├── transactions     — 所有交易
  ├── token_transfers  — 代币转账事件
  ├── address_coin_balances — 地址余额历史
  ├── tokens           — 代币元数据
  ├── smart_contracts  — 已验证的合约源码
  ├── logs             — 事件日志
  └── internal_transactions — 内部交易
       │
       ▼
  REST API + GraphQL
       │
       ▼
  Next.js 前端
```

### 2.2 Subscan（Go 语言，Substrate 生态浏览器）

```
技术栈：Go + PostgreSQL + Redis + Elasticsearch
特点：
  - 用 Go 写的，和我们语言相同
  - 微服务架构，每个链一个 Worker
  - 通过 Substrate 的 Runtime Metadata 动态解码
  - 支持 Polkadot/Kusama 等多条链
```

### 2.3 Tokenview / OKLink（商业级多链浏览器）

```
Tokenview: 200+ 链，节点层 + ETL + DB + API + 前端
OKLink: 30+ 链，跨链地址搜索，合规工具，DeFi/NFT 数据

共同特点：
  - 每条链跑自己的全节点/归档节点
  - 统一的数据模型（归一化不同链的差异）
  - PostgreSQL/Elasticsearch 做存储
  - Redis 做热数据缓存
  - 前端可按链切换，数据格式统一
```

## 四、数据库 Schema 设计

### 4.1 核心表

```sql
-- ============================================================
-- 区块表
-- ============================================================
CREATE TABLE blocks (
    id            BIGINT AUTO_INCREMENT PRIMARY KEY,
    chain         VARCHAR(20)  NOT NULL,           -- 'eth', 'bsc', 'polygon'
    block_number  BIGINT       NOT NULL,
    block_hash    VARCHAR(66)  NOT NULL,           -- 0x...
    parent_hash   VARCHAR(66)  NOT NULL,
    timestamp     DATETIME     NOT NULL,
    miner         VARCHAR(42),                     -- 出块者地址
    gas_used      BIGINT,
    gas_limit     BIGINT,
    base_fee      VARCHAR(30),                     -- EIP-1559 base fee
    tx_count      INT          DEFAULT 0,
    size          BIGINT,
    extra_data    TEXT,
    created_at    DATETIME     DEFAULT CURRENT_TIMESTAMP,
    UNIQUE KEY uk_chain_block (chain, block_number),
    UNIQUE KEY uk_chain_hash  (chain, block_hash),
    INDEX idx_chain_time      (chain, timestamp)
);

-- ============================================================
-- 交易表
-- ============================================================
CREATE TABLE transactions (
    id            BIGINT AUTO_INCREMENT PRIMARY KEY,
    chain         VARCHAR(20)  NOT NULL,
    tx_hash       VARCHAR(66)  NOT NULL,
    block_number  BIGINT       NOT NULL,
    tx_index      INT          NOT NULL,           -- 交易在区块中的位置
    from_address  VARCHAR(42)  NOT NULL,
    to_address    VARCHAR(42),                     -- 合约创建交易为 NULL
    value         VARCHAR(78)  NOT NULL,           -- uint256 原始值（Wei/Lamports）
    value_decimal VARCHAR(30),                     -- 归一化后的值（如 1.5 ETH）
    gas_price     VARCHAR(30),
    gas_used      BIGINT,
    gas_fee       VARCHAR(30),                     -- 实际花费的 Gas 费
    status        TINYINT,                         -- 1=成功, 0=失败
    nonce         BIGINT,
    input_data    LONGTEXT,                        -- 合约调用数据
    method_id     VARCHAR(10),                     -- 函数选择器 (0xa9059cbb = transfer)
    method_name   VARCHAR(100),                    -- 解码后的函数名
    timestamp     DATETIME     NOT NULL,
    created_at    DATETIME     DEFAULT CURRENT_TIMESTAMP,
    UNIQUE KEY uk_chain_tx    (chain, tx_hash),
    INDEX idx_chain_block     (chain, block_number),
    INDEX idx_chain_from      (chain, from_address),
    INDEX idx_chain_to        (chain, to_address),
    INDEX idx_chain_time      (chain, timestamp)
);

-- ============================================================
-- 代币转账事件表（ERC-20 Transfer / ERC-721 Transfer）
-- ============================================================
CREATE TABLE token_transfers (
    id              BIGINT AUTO_INCREMENT PRIMARY KEY,
    chain           VARCHAR(20)  NOT NULL,
    tx_hash         VARCHAR(66)  NOT NULL,
    log_index       INT          NOT NULL,
    block_number    BIGINT       NOT NULL,
    contract        VARCHAR(42)  NOT NULL,         -- 代币合约地址
    from_address    VARCHAR(42)  NOT NULL,
    to_address      VARCHAR(42)  NOT NULL,
    token_id        VARCHAR(78),                   -- NFT 的 token ID
    amount          VARCHAR(78),                   -- ERC-20 转账金额（原始值）
    amount_decimal  VARCHAR(30),                   -- 归一化后的金额
    token_standard  VARCHAR(10),                   -- 'erc20', 'erc721', 'erc1155'
    event_type      VARCHAR(20),                   -- 'transfer', 'mint', 'burn'
    timestamp       DATETIME     NOT NULL,
    created_at      DATETIME     DEFAULT CURRENT_TIMESTAMP,
    UNIQUE KEY uk_chain_tx_log (chain, tx_hash, log_index),
    INDEX idx_chain_contract   (chain, contract),
    INDEX idx_chain_from       (chain, from_address),
    INDEX idx_chain_to         (chain, to_address),
    INDEX idx_chain_time       (chain, timestamp)
);

-- ============================================================
-- 事件日志表（所有智能合约事件）
-- ============================================================
CREATE TABLE event_logs (
    id            BIGINT AUTO_INCREMENT PRIMARY KEY,
    chain         VARCHAR(20)  NOT NULL,
    tx_hash       VARCHAR(66)  NOT NULL,
    log_index     INT          NOT NULL,
    block_number  BIGINT       NOT NULL,
    contract      VARCHAR(42)  NOT NULL,
    topic0        VARCHAR(66),                    -- 事件签名哈希
    topic1        VARCHAR(66),
    topic2        VARCHAR(66),
    topic3        VARCHAR(66),
    data          LONGTEXT,                       -- 事件数据
    event_name    VARCHAR(100),                   -- 解码后的事件名
    event_data    JSON,                           -- 解码后的参数
    timestamp     DATETIME     NOT NULL,
    created_at    DATETIME     DEFAULT CURRENT_TIMESTAMP,
    UNIQUE KEY uk_chain_tx_log (chain, tx_hash, log_index),
    INDEX idx_chain_contract   (chain, contract),
    INDEX idx_chain_topic0     (chain, topic0),
    INDEX idx_chain_time       (chain, timestamp)
);

-- ============================================================
-- 地址表
-- ============================================================
CREATE TABLE addresses (
    id             BIGINT AUTO_INCREMENT PRIMARY KEY,
    chain          VARCHAR(20)  NOT NULL,
    address        VARCHAR(42)  NOT NULL,
    balance        VARCHAR(78)  DEFAULT '0',      -- 原生币余额（Wei）
    balance_decimal VARCHAR(30) DEFAULT '0',      -- 归一化余额
    tx_count       BIGINT       DEFAULT 0,        -- 作为 from 或 to 的交易数
    first_seen_at  DATETIME,                      -- 首次出现的区块时间
    last_seen_at   DATETIME,                      -- 最后活动时间
    is_contract    TINYINT      DEFAULT 0,        -- 是否是合约地址
    updated_at     DATETIME     DEFAULT CURRENT_TIMESTAMP ON UPDATE CURRENT_TIMESTAMP,
    UNIQUE KEY uk_chain_addr   (chain, address),
    INDEX idx_chain_balance    (chain, balance),
    INDEX idx_chain_last_seen  (chain, last_seen_at)
);

-- ============================================================
-- 代币元数据表
-- ============================================================
CREATE TABLE tokens (
    id              BIGINT AUTO_INCREMENT PRIMARY KEY,
    chain           VARCHAR(20)  NOT NULL,
    contract        VARCHAR(42)  NOT NULL,
    name            VARCHAR(200),
    symbol          VARCHAR(50),
    decimals        INT,
    total_supply    VARCHAR(78),
    token_standard  VARCHAR(10),                  -- 'erc20', 'erc721', 'erc1155'
    holder_count    BIGINT       DEFAULT 0,
    transfer_count  BIGINT       DEFAULT 0,
    first_seen_at   DATETIME,
    created_at      DATETIME     DEFAULT CURRENT_TIMESTAMP,
    updated_at      DATETIME     DEFAULT CURRENT_TIMESTAMP ON UPDATE CURRENT_TIMESTAMP,
    UNIQUE KEY uk_chain_contract (chain, contract),
    INDEX idx_chain_symbol       (chain, symbol)
);

-- ============================================================
-- 索引进度表（每条链记录同步到哪个区块了）
-- ============================================================
CREATE TABLE indexer_state (
    chain           VARCHAR(20)  PRIMARY KEY,
    last_block      BIGINT       NOT NULL DEFAULT 0,
    last_hash       VARCHAR(66),
    is_syncing      TINYINT      DEFAULT 0,
    blocks_behind   BIGINT       DEFAULT 0,       -- 跟链最新区块的差距
    updated_at      DATETIME     DEFAULT CURRENT_TIMESTAMP ON UPDATE CURRENT_TIMESTAMP
);

-- ============================================================
-- 链配置表（数据库驱动，不用改代码）
-- ============================================================
CREATE TABLE chains (
    id              INT AUTO_INCREMENT PRIMARY KEY,
    network         VARCHAR(20)  NOT NULL UNIQUE,  -- 'eth', 'bsc', 'polygon'
    display_name    VARCHAR(50)  NOT NULL,         -- 'Ethereum', 'BNB Chain'
    chain_id        INT,                           -- EVM chain ID
    native_symbol   VARCHAR(10),                   -- 'ETH', 'BNB'
    native_decimals INT          DEFAULT 18,
    explorer_url    VARCHAR(200),                  -- 官方浏览器 URL
    enabled         TINYINT      DEFAULT 1,
    created_at      DATETIME     DEFAULT CURRENT_TIMESTAMP
);

-- ============================================================
-- RPC 节点配置表
-- ============================================================
CREATE TABLE rpc_nodes (
    id              INT AUTO_INCREMENT PRIMARY KEY,
    network         VARCHAR(20)  NOT NULL,
    url             VARCHAR(500) NOT NULL,
    type            VARCHAR(10)  NOT NULL,         -- 'http', 'ws'
    weight          INT          DEFAULT 100,      -- 权重（越高越优先）
    enabled         TINYINT      DEFAULT 1,
    status          TINYINT      DEFAULT 1,        -- 1=健康, 0=不健康
    last_latency_ms INT,
    last_checked_at DATETIME,
    created_at      DATETIME     DEFAULT CURRENT_TIMESTAMP,
    INDEX idx_network_enabled (network, enabled)
);
```

### 4.2 数据量估算

| 链 | 区块/天 | 交易/天 | 代币转账/天 | 存储/月 |
|---|---|---|---|---|
| Ethereum | ~7,200 | ~1,100,000 | ~5,000,000 | ~30 GB |
| BSC | ~28,800 | ~3,500,000 | ~15,000,000 | ~80 GB |
| Polygon | ~43,200 | ~2,500,000 | ~10,000,000 | ~60 GB |
| Solana | ~216,000 | ~40,000,000 | ~20,000,000 | ~200 GB |
| TRON | ~86,400 | ~5,000,000 | ~8,000,000 | ~50 GB |

**注意：** 全量索引 5 条链一个月需要 ~420 GB。长期运营需要考虑数据归档策略。
初期建议只支持 2-3 条链，每条链索引最近 N 个区块。

### 5.2 关键设计决策

#### 决策 1：要不要消息队列（RabbitMQ/Kafka）？

**结论：初期不需要。**

```
场景分析：

区块链浏览器 vs 支付网关 vs 事件索引器

epusdt（支付网关）：    Listener → 直接处理 → DB        ✅ 没用 MQ
Blockscout（浏览器）：  Indexer → Pipeline → DB          ✅ 没用 MQ
Tokenview（浏览器）：   Node → ETL → DB                  ✅ 没用 MQ
我们的旧方案：          Listener → RabbitMQ → Processor   ❌ 过度设计

为什么区块链浏览器不需要 MQ？
1. 数据流向单一：链 → DB → API，不需要扇出给多个消费者
2. 吞吐量瓶颈在 RPC，不在处理速度：一个 RPC 节点每秒最多返回几十个区块
3. 顺序性要求高：区块必须按顺序处理，MQ 会引入乱序风险
4. 运维复杂度：多一个中间件就多一个故障点

什么时候需要 MQ？
- 同一份数据要分发给多个消费者（如同时写 DB + 触发 Webhook + 推送 WebSocket）
- 需要水平扩展处理能力（多个 Processor 实例消费同一队列）
- 我们的场景：单个 Indexer 进程直接写 DB，足够了
```

#### 决策 2：要不要 Redis？

**结论：需要，但用途有限。**

```
Redis 在区块链浏览器中的合理用途：
1. API 响应缓存（TTL 30 秒）：最新区块列表、统计数据、热门代币
2. 搜索结果缓存：用户搜索地址/交易哈希的结果
3. 实时计数器：总交易数、总区块数的自增

Redis 不应该做的事（旧方案的错误）：
1. ❌ 存储事件数据（应该在 PostgreSQL 里）
2. ❌ 存储最新 N 条交易（应该从 DB 查）
3. ❌ 作为消息队列（应该用 MQ 或直接处理）
```

#### 决策 3：goroutine 用在哪里？

```
正确用法（epusdt/Blockscout 的模式）：

每条链一个 goroutine：
  go runChainWorker("eth", ...)   ← 独立的 ETH 索引循环
  go runChainWorker("bsc", ...)   ← 独立的 BSC 索引循环
  go runChainWorker("sol", ...)   ← 独立的 SOL 索引循环

每条链内部是串行的：
  for each new block:
      1. fetch block + transactions     ← 顺序
      2. decode logs/events             ← 顺序
      3. update addresses               ← 顺序
      4. write to DB                    ← 顺序
      5. update indexer_state           ← 顺序

错误用法（旧方案的问题）：
  ❌ 一个 goroutine 监听所有链（混在一起）
  ❌ 用 channel/RabbitMQ 在 goroutine 间传递（增加复杂度）
  ❌ 并发写 DB（引入竞态条件）
```

#### 决策 4：微服务还是单体？

**结论：单体，但模块化。**

```
为什么不需要微服务：
1. 团队规模小（1-2 人），微服务的运维开销不值得
2. 所有组件共享同一个 PostgreSQL，拆服务只是多了一层网络调用
3. 部署简单：一个二进制文件 + docker-compose

模块化单体：
  main.go
  ├── indexer/          ← 索引器模块
  │   ├── manager.go    ← 链管理器
  │   ├── eth_worker.go ← ETH 索引
  │   ├── bsc_worker.go ← BSC 索引
  │   └── sol_worker.go ← SOL 索引
  ├── api/              ← REST API 模块
  │   ├── router.go
  │   ├── block_handler.go
  │   ├── tx_handler.go
  │   └── address_handler.go
  ├── model/            ← 数据模型 + DB 操作
  │   ├── block.go
  │   ├── transaction.go
  │   └── address.go
  └── config/           ← 配置

一个二进制，两个模式：
  ./explorer serve api        ← 只启动 API 服务
  ./explorer serve indexer    ← 只启动索引器
  ./explorer serve all        ← 同时启动（开发/小规模部署）
```

## 六、与 epusdt 的架构对比

| 维度 | epusdt（支付网关） | 我们的目标（区块链浏览器） |
|------|-------------------|------------------------|
| 核心业务 | 检测支付到账 | 索引全量链上数据 |
| 监听范围 | 只关心特定地址的转账 | 索引所有区块、所有交易 |
| 数据模型 | 订单 + 钱包 + 锁 | 区块 + 交易 + 地址 + 代币 + 日志 |
| 链配置 | chains + chain_tokens 表 | chains + rpc_nodes 表 |
| WebSocket | ✅ EVM 链用 WS 订阅 | ✅ EVM 链用 WS 订阅 |
| 热加载 | ✅ Watchdog | ✅ Config Watchdog |
| RPC 管理 | ✅ 多节点 + 健康检查 | ✅ 多节点 + 健康检查 |
| 消息队列 | ❌ 不需要 | ❌ 不需要 |
| 直接写 DB | ✅ | ✅ |
| 可以复用的模式 | EVM WS 监听、Watchdog、RPC 管理 | 全部可以复用 |

**结论：epusdt 的架构模式几乎可以原样移植到区块链浏览器，只需要把"支付检测"逻辑替换为"全量索引"逻辑。**

## 九、风险与挑战

| 风险 | 影响 | 应对方案 |
|------|------|---------|
| RPC 节点限速 | 索引速度慢 | 付费节点（Alchemy/Infura）+ 多节点轮询 |
| 数据量过大 | 磁盘/查询性能 | 只索引最近 N 个区块 + 定期归档 |
| 链重组（Reorg） | 数据不一致 | 监测重组深度，回滚已索引的区块 |
| 公共 RPC 不稳定 | 索引中断 | 重试机制 + 节点切换 |
| Solana 数据量巨大 | 存储成本 | 可选：只索引涉及特定程序的交易 |

## 十、结论

**可行性：完全可行。**

1. 区块链浏览器的核心逻辑（索引 → 存储 → 查询 → 展示）是成熟模式
2. epusdt 的架构模式（WebSocket 监听、Watchdog 热加载、RPC 管理）可以直接复用
3. 不需要微服务、不需要消息队列、不需要过度设计
4. Go 语言 + PostgreSQL + Redis + Echo 是经过验证的技术栈
5. 开发路线图清晰，4 个阶段约 6-8 周可以完成 MVP

**最大的改变：**
- 从"事件监听器"变成"全量数据索引器"
- 从"硬编码"变成"数据库驱动"
- 从"轮询"变成"WebSocket + 轮询混合"
- 从"微服务 + MQ"变成"模块化单体 + 直接写 DB"
